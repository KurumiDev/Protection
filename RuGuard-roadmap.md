## 0. Оценка текущего состояния (факт против спеки §3)

Перед планированием проведён аудит кодовой базы. Реальность существенно расходится с §3.

| Слой | Что требует спека | Что есть по факту | Разрыв |
|------|-------------------|-------------------|--------|
| Build-time трансформер | Kotlin + ObjectWeb ASM | `jvm/cryptor` — **рукописный Java-парсер** classfile, **без build-файла** (россыпь `.java`, `inst.txt`: «собрать в проект вручную»). Линейный байтовый ре-энкодер: XOR-ит constant pool, ремапит теги, XOR-ит UTF8. **Нет модели CFG, операндов, stackmap-фреймов.** `parseCodeAttribute` читает опкоды, но пишет их без изменений. | **Критический.** Рубеж B (chunk decrypt/execute/wipe, flattening) требует базовых блоков, анализа операндов и пересчёта stackmap — ничего из этого рукописный парсер не умеет. |
| Формат вывода | Валидный classfile + зашифрованные chunk'и в constant pool | **Невалидный classfile**: теги ремапнуты (Utf8→90 и т.п.), short'ы XOR-нуты и перемешаны со случайным padding и байтами ключа. Загружается только парным рантайм-декодером (который в аудите не локализован явно). | Есть скрытая зависимость: build-энкодер ↔ рантайм-декодер. Любая миграция обязана сохранить или заменить обе стороны согласованно. |
| Крипто | ChaCha20-Poly1305 + HKDF от runtime-энтропии | Ad-hoc XOR + `pack()` (битовые сдвиги), ключ = 4 рандома, записанные **в сам файл**. | **P2 нарушен**: ключ статически восстановим из файла. Ровно проблема §6.4, которую Рубеж B закрывает. |
| Нативный барьер | **Rust** (`jni-rs`, `#![no_std]`), **свой packer, НЕ VMProtect** (§8.4) | `native/WissendNative` — Maven **Java→C++ транспайлер** (клон native-obfuscator: `@Native`, `Preprocessor`, `native_jvm.cpp`, `handler.cpp`, `VMProtectClassSourceBuilder`), пакует **коммерческим VMProtect SDK** (`VMProtectSDK.h`). | **Прямой конфликт с §8.4 и P6.** VMProtect сигнатурится AV/EDR, есть публичные unpacker'ы. Спека это запрещает явно. **Требуется решение (см. §5, Решение D1).** |
| Репозиторий | Gradle multi-module + Cargo workspace | Maven + россыпь Java + C++ `.sln`. **Rust — 0 файлов. Kotlin — 0. Gradle — 0.** | Фундамент §3 не заложен. |
| Лоадер | — (вне рубежей, но часть продукта) | `loader/WissedLoader` — C++ VS-проект: `AuthUtils`, `Download`, `MinecraftLoader`, `md5`, `unzip`. Аутентификация + запуск Minecraft/мода. | Естественная точка для Рубежа F (allow-list attach, ранний JVMTI-агент) в поздней фазе. |
| Бэкенд | — | `server/WissendBackend` (деплой-копия, есть `build.bat`) + `src/WissendBackend` (дубликат). Maven/Spring. Логика подписки/HWID. | Два клона — риск дрейфа. Нужна консолидация до одного источника. |

**Вывод по оценке (ответ на вопрос «движок»):** текущий рукописный парсер — тупик для Рубежей B–C.
Он не даёт CFG, не резолвит операнды переходов, не умеет пересчитывать stackmap-фреймы (обязательны с
classfile v51+). Наращивать на нём flattening = переписать половину ASM вручную и хуже. **Рекомендация:
мигрировать трансформер на Kotlin + ASM (как и предписывает §3), это первый под-шаг Фазы 1.** Рукописный
парсер сохраняем как reference для формата рантайм-декодера, но новый pipeline строим на ASM.

## 2. Целевая структура репозитория (к чему идём, §3)

```
ruguard/                         (Gradle root: settings.gradle.kts)
├─ ruguard-cli/                  Kotlin + ASM — трансформер этапа сборки (Рубежи A,B,C-gen)
│  ├─ core/                      ASM-пассы: chunk, flatten, opaque, string-crypto
│  ├─ crypto/                    ChaCha20-Poly1305 + HKDF (build-side)
│  ├─ isa/                       DSL-кодогенератор ISA VM (per-build seed)
│  └─ runtime-glue/              генерация bootstrap-вызовов
├─ ruguard-runtime/              Java — рантайм-декодер chunk'ов, Java-VM-интерпретатор (до Фазы 5)
├─ ruguard-native/               Rust (Cargo workspace) — JNI-барьер, JVMTI-агент, native-VM, packer
│  ├─ barrier/                   license/integrity/anti-debug, источник энтропии для HKDF
│  ├─ jvmti-agent/               Рубеж F (поздняя фаза)
│  └─ packer/                    свой ChaCha20/XOR packer (замена VMProtect, §8.4)
├─ ruguard-redteam/              dump/attach-атаки, обязательный CI-gate (§11)
├─ loader/                       (существующий C++) — интеграция Рубежа F позже
└─ server/                       (консолидированный бэкенд) — валидация лицензии/HWID
```

Миграция — инкрементальная: на каждой фазе Maven-модуль, которого касаемся, переезжает в Gradle/Cargo.
Существующий `native/WissendNative` живёт параллельно как interim до Фазы 5.

## 3. Сквозные рабочие продукты (делаются рано, используются всеми фазами)

Эти вещи не привязаны к одной фазе — их закладываем в Фазе 1 и переиспользуем.

- **S1. redteam-каркас (`:ruguard-redteam`).** Даже пустой — до первой защиты. Прогоняет Recaf attach,
  JVMTI class-retransform дампер, async-profiler memory-dump против собранного билда. Возвращает
  PASS(атака удалась)/FAIL(атака сломалась). CI-gate: PASS атаки = билд НЕ публикуется (§11).
- **S2. Build-seed инфраструктура (§9.1).** Детерминированный seed из CI build number → полиморфизм
  (перестановки ISA, порядок integrity-проверок, границы chunk'ов, opaque predicates). Один источник
  seed'а, потребляется всеми пассами.
- **S3. `@Guarded` / `@Native` аннотации (§6.3).** Разметка методов под выборочную защиту — flattening и
  VM применяются только к помеченному (тотальный flattening убивает tick-performance).
- **S4. Golden-тесты корректности.** Для каждого защищаемого метода — тест «защищённый даёт тот же
  результат, что оригинал» на корпусе входов. Без этого любой пасс = риск тихой поломки продукта.

## 4. Фазы (строго по §12, каждая — отдельный PR + redteam-gate)

### Фаза 0 — Фундамент (не в §12, но необходим; отдельный PR)
**Цель:** заложить каркас, не меняя поведения продукта.
- [ ] Gradle root + `:ruguard-cli` (Kotlin, ASM-зависимость), `:ruguard-runtime`, `:ruguard-redteam` (S1).
- [ ] Портировать существующий рукописный энкодер в ASM-эквивалент: **байт-в-байт тот же выходной
      формат**, но через `ClassReader`/`ClassWriter`/`ClassVisitor`. Reference — `jvm/cryptor`.
- [ ] Golden-тесты (S4): старый и новый энкодер дают идентичный выход на тестовом jar.
- [ ] Build-seed (S2) + `@Guarded` (S3) заглушки.
- **Gate:** новый pipeline воспроизводит текущую защиту 1:1; redteam-каркас запускается (пусть пока
  атаки проходят — фиксируем baseline).
- **Зависит от:** —

### Фаза 1 — Рубеж B базовый: chunk decrypt→execute→wipe + HKDF (§6.1, §6.2, §6.4)
**Цель:** топ-10 ценных методов защищены посегментной крипто-схемой; ключи — производные рантайма.
- [ ] ASM-пасс: разбиение метода на basic blocks по CFG; каждый блок → зашифрованный байт-массив в
      constant pool (ChaCha20-Poly1305).
- [ ] Bootstrap-механизм: перед входом в блок — `deriveKey(state)` → `decrypt` → `exec` → `wipe`.
- [ ] **Wipe, устойчивый к JIT** (§6.1): `Reference.reachabilityFence` + volatile, либо native
      zero-wipe через JNI. Проверить, что JIT не элиминирует (тест на escape-анализ).
- [ ] **Scope-binding (инвариант §6.1):** ключ блока N зависит от результата исполнения блока N-1
      (хэш локальных на выходе). Дамп блока в изоляции нерасшифровываем.
- [ ] HKDF-деривация (§6.2) из: `nanoTime`-снимок старта, хэш classloader'ов, (заглушка под native-
      энтропию Фазы 3), опц. хэш контрольных полей владельца.
- [ ] Строки/константы (§6.4): ключ = `HKDF(per-build master secret, class-hash, index)`. Master
      secret инжектится на CI, **в classfile его нет** (до Фазы 3 — временно в рантайме, с TODO-переносом
      в native).
- **Gate (§11):** redteam — статический дамп даёт зашифрованные chunk'и; нельзя получить валидный
      исполняемый classfile; ключ не выводится статически. Golden-тесты зелёные.
- **Зависит от:** Фаза 0. Инварианты: **P1** (нет целостного plaintext), **P2** (нет статических ключей).

### Фаза 2 — Control-flow flattening + opaque predicates, выборочно `@Guarded` (§6.3)
**Цель:** CFG помеченных методов уплощён, переходы скрыты за opaque-предикатами.
- [ ] ASM-пасс: CFG → dispatch-loop `while(true){ switch(state){...} }`.
- [ ] Переходы состояний = результат opaque predicate (не литералы), напр. `(x*x - x) % 2 == 0`.
- [ ] Применять **только** к `@Guarded` (S3); real-time detect-циклы не трогать (perf).
- [ ] Композиция с Фазой 1: flattening поверх chunk-crypto (порядок пассов зафиксировать и покрыть
      golden-тестами).
- [ ] Бюджет производительности: бенчмарк tick-времени до/после на реальном моде.
- **Gate:** redteam-декомпиляторы (CFR/Procyon/Vineflower) не восстанавливают исходный поток;
      perf-регресс в пределах бюджета; golden зелёные.
- **Зависит от:** Фаза 1.

### Фаза 3 — Рубеж D: нативный барьер на Rust (license/integrity/anti-debug) + JNI-энтропия (§8)
**Цель:** Rust-слой как независимый рубеж и источник энтропии, связывающий Java- и native-слои.
- [ ] `:ruguard-native/barrier` (Rust, `jni-rs`, `#![no_std]` для критичных участков).
- [ ] JNI-мост — **источник энтропии** для HKDF Фазы 1 (закрыть заглушку §6.2 п.3). Теперь дамп
      одного слоя бесполезен без другого (P6).
- [ ] Anti-debug ≥4 механизма (§8.2), каждый — **тихая деградация** (P4), не abort:
      (1) `-agentlib`/`jdwp`-детект → сдвиг одного байта derived key; (2) `rdtsc` timing;
      (3) hardware breakpoint DR0–DR7 (`GetThreadContext`/`ptrace`); (4) self-attach test.
- [ ] Integrity — **распределённо** (§8.3): 50–100 мелких хэш-проверок, инжектируемых ASM-пассом в
      случайные точки; результат входит множителем в деривацию ключа chunk'а (не `if/throw`).
- [ ] Мастер-секрет строк (§6.4) переезжает в native-слой (закрыть TODO Фазы 1).
- [ ] **D1:** начать выпил VMProtect — свой минимальный packer (§8.4): ChaCha20/XOR поверх `.text`,
      unpack-stub, самозатирание stub'а. Обфускация экспортов через `JNI_OnLoad`.
- **Gate:** redteam — attach/timing-атаки ведут к тихой деградации, не к явному отказу; дамп Java-слоя
      без native не даёт ключей; свой packer проходит AV-скан чище, чем VMProtect-сборка.
- **Зависит от:** Фаза 1 (мост закрывает её заглушку). Инвариант **P3** (≥3 механизма), **P6**.

### Фаза 4 — Рубеж C: custom VM, Java-интерпретатор, 3–5 ценных алгоритмов (§7)
**Цель:** самое ценное IP виртуализировано в полиморфной stack-based VM.
- [ ] ISA-DSL/кодогенератор (Kotlin, §7.2): 40–60 избыточных опкодов, `opcode→handler` перемешивается
      из build-seed (S2). Диспетчеризация — computed indirect call по зашифрованной таблице (не switch).
- [ ] Java-интерпретатор (`:ruguard-runtime`), тело интерпретатора само под chunk decrypt/exec/wipe (§7.2).
- [ ] ASM-пасс: трансляция `@Guarded`-алгоритмов детекта/лицензии/фич-экстракции в байткод VM.
- [ ] Полиморфизм ISA per-build (P5): реверс одного билда не даёт девиртуализатор для следующего.
- **Gate:** redteam-«девиртуализатор» на билде N не применяется к билду N+1; golden-тесты алгоритмов
      зелёные; perf в бюджете.
- **Зависит от:** Фазы 2 и 3.

### Фаза 5 — Перенос VM-интерпретатора в native (Rust), если экономика оправдывает (§7.3)
**Цель:** самые ценные алгоритмы — только в Rust-VM (реверс требует IDA/Ghidra + разбор кастомного ISA).
- [ ] Порт интерпретатора в `:ruguard-native`.
- [ ] **Завершить D1/D2:** ценные алгоритмы уходят из Java→C++ транспайлера (VMProtect) в Rust-VM;
      `native/WissendNative` выводится из критического пути.
- **Gate:** дамп памяти не даёт исполняемого представления алгоритма; редтим не восстанавливает ISA.
- **Зависит от:** Фаза 4. **Условно** — делать, только если ROI оправдывает (§7.3, §12).

### Фаза 6 — Рубеж E (полиморфизм сборки) + редтим как обязательный gate (§9, §11)
**Цель:** каждый релиз — уникальная полиморфная перестановка; редтим встроен в CI жёстко.
- [ ] Всё из S2 сведено: per-build seed управляет ISA, порядком integrity-проверок, opaque-набором,
      границами chunk'ов.
- [ ] **Per-client билды** (§9.1): по возможности отдельная полиморфная сборка на покупателя — ломает
      сценарий «взломал раз — раздал всем».
- [ ] Редтим — блокирующий CI-gate на каждый билд (§11): дамп-атака прошла → релиз заблокирован.
- [ ] (Опц.) Рубеж F (§10): свой JVMTI-агент в jlink-образе, allow-list attach через `loader/` — **только
      для standalone-лаунчера** (§9.2); для серверного плагина не делаем.
- **Gate:** матрица редтим-атак красная (все атаки сломаны) на N случайных полиморфных билдах.
- **Зависит от:** все предыдущие.

## 6. Открытые вопросы к владельцу

- **Q1 (D1):** ок ли план выпиливать VMProtect к Фазе 3–5 и заменить своим Rust-packer'ом? Это
  требование §8.4, но затрагивает работающий продукт.
- **Q2 (§9.2):** дистрибуция — standalone-лаунчер (тогда Рубеж F в игре) или серверный плагин (тогда
  Рубеж F не делаем, бюджет — в C–D)? Наличие `loader/WissedLoader` намекает на standalone.
- **Q3 (D3):** какой из двух бэкендов (`server/` vs `src/`) канонический? Второй удалить.
- **Q4:** есть ли CI (спека опирается на CI build-seed, §9.1) или его тоже поднимаем с нуля?
```
