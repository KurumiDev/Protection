# RuGuard — спецификация защиты JVM-байткода

> **Статус документа:** источник истины для итеративной разработки. Файл описывает
> архитектуру, технологические решения и порядок реализации протектора уровня
> топ-индустрии (класс VMProtect / Themida, адаптированный под JVM).
>
> Конкретный код агент пишет по месту. Здесь зафиксированы **инварианты**, которые
> нельзя нарушать ни на одной итерации, и **порядок работ**, который нельзя перепрыгивать.

---

## 1. Назначение и модель угроз

RuGuard — build-time тулчейн, защищающий коммерческий JVM-продукт (визуальный мод,
распространяемый по подписке) от:

- кракинга подписочной/лицензионной логики;
- дампа байткода из работающей JVM;
- декомпиляции и восстановления исходников;
- массового распространения одного взлома на всех пользователей.

**Кого мы моделируем как атакующего.** Профильный реверс-инженер с IDA/Ghidra, Recaf,
JVMTI-инструментами и опытом снятия защиты с JVM-приложений. Цель RuGuard — не
«неснимаемость», а перевод стоимости взлома в диапазон «недели целенаправленной работы»,
что делает крак экономически нерентабельным относительно цены подписки.

**Что вне модели.** Полный патчинг исходников HotSpot (`bytecodeInterpreter.cpp`) — отдельный
проект, сопоставимый по сложности с самим продуктом. Он рассматривается только как резерв
(см. §11), если после прохождения всех фаз редтим найдёт рабочий обход именно на уровне
JVMTI-барьера.

## 2. Незыблемые принципы

Эти шесть правил приоритетнее любых соображений «нагляднее / быстрее закодить».
При любой неоднозначности реализации сверяемся с ними, а не с удобством.

| # | Принцип | Формулировка |
|---|---------|--------------|
| P1 | **Нет целостного plaintext** | Никогда не существует момента, когда весь защищённый артефакт расшифрован в памяти целиком. Расшифровка — только посегментно, с немедленным затиранием сегмента после исполнения. |
| P2 | **Нет статических ключей** | Ни один ключ дешифровки не хранится как константа — ни в коде, ни в native-секции, ни в ресурсах. Ключ всегда является производной функцией от состояния рантайма. |
| P3 | **Нет единой точки отказа** | Каждый критичный инвариант (integrity, наличие отладчика, лицензия) проверяется минимум **тремя** независимыми, физически разнесёнными по кодовой базе механизмами. |
| P4 | **Тихая деградация вместо краша** | Провал проверки никогда не выражается явным немедленным crash/exception в точке проверки. Реакция отложена и/или замаскирована под обычный баг. |
| P5 | **Полиморфизм ISA** | Набор инструкций виртуальной машины уникален для каждой сборки. Реверс одного билда не даёт автоматического девиртуализатора для следующего. |
| P6 | **Раздельная самозащита слоёв** | Native-слой защищён отдельно от Java-слоя. Компрометация одного не обнажает автоматически другой. |

## 3. Технологические решения

| Компонент | Выбор | Почему именно так |
|-----------|-------|-------------------|
| Движок трансформации байткода | **ObjectWeb ASM** | Низкоуровневый доступ без накладных расходов Javassist. Необходим для flattening и кастомного ISA. |
| Build-time протектор (CLI) | **Kotlin на JVM** | Меньше boilerplate, чем Java; полная совместимость с ASM/JVM-экосистемой. |
| Нативный самозащитный слой | **Rust** (не C++) | Memory-safety снижает шанс exploitable-бага в самом протекторе. `#![no_std]`-секции для критичных участков. |
| JNI / FFI мост | **jni-rs** или ручной JNI (не JNA) | JNA — известная библиотека; её присутствие в classpath само по себе маркер для реверсера. |
| Шифрование сегментов | **ChaCha20-Poly1305** (не AES) | Нет side-channel через AES-NI кэш-тайминги; constant-time реализация проще. |
| Деривация ключей | **HKDF** с runtime-энтропией как input keying material | Ключ невозможно вычислить статическим анализом — он функция состояния. |
| Генератор ISA | Собственный **DSL/кодогенератор на Kotlin**, работает на этапе build | Каждая сборка получает свою таблицу опкодов. |
| Anti-debug (JVM) | JVMTI-проверки + кастомный `-javaagent`-детектор + анализ runtime-аргументов `ManagementFactory` | — |
| Anti-debug (OS) | Rust: проверка debug-портов, timing через `rdtsc` / `QueryPerformanceCounter` | — |
| Кастомный образ рантайма (опц., поздняя фаза) | `jlink` + JVMTI-хуки | Только для контролируемой дистрибуции; см. §10. |
| CI/CD | **Gradle multi-module + Cargo workspace** | Воспроизводимость; полиморфизм генерируется детерминированно на CI, но по-разному на каждый релиз. |
| Стенд самопроверки | Отдельный модуль редтима | Собственный «реверсер», который должен ломаться как можно дольше. |

**Структура репозитория:**

```
:ruguard-cli         — Kotlin, ASM-трансформер этапа сборки
:ruguard-runtime     — Java-компоненты рантайма (VM-интерпретатор, до поздней фазы)
:ruguard-native      — Rust: JNI-барьер, JVMTI-агент, native VM-интерпретатор
:ruguard-redteam     — самотестирование: dump/attach-атаки на каждый CI-билд
```

Rust собирается в общий pipeline через `cargo-ndk` / `cross` с JNI-биндингами.

## 4. Модель защиты: шесть рубежей

Защита эшелонирована. Каждый рубеж работает независимо — компрометация нижнего не даёт
автоматического доступа к верхнему.

```
┌───────────────────────────────────────────────┐
│ Рубеж F: кастомный JRE / JVMTI-хуки (опц.)     │  дистрибутивный, поздняя фаза
├───────────────────────────────────────────────┤
│ Рубеж E: сборка и полиморфизм дистрибуции      │  версионирование ISA, per-build seed
├───────────────────────────────────────────────┤
│ Рубеж D: нативный самозащитный барьер (Rust)   │  license / integrity / anti-debug, packed
├───────────────────────────────────────────────┤
│ Рубеж C: полиморфная виртуальная машина        │  виртуализация горячих алгоритмов
├───────────────────────────────────────────────┤
│ Рубеж B: поток управления и строки             │  flattening, opaque predicates, chunk-crypto
├───────────────────────────────────────────────┤
│ Рубеж A: обфускация идентификаторов            │  базовый слой (уже есть)
└───────────────────────────────────────────────┘
```

Дальше — детальная спецификация каждого рубежа.

## 5. Рубеж A — обфускация идентификаторов

Базовый слой переименования классов/методов/полей. Он уже реализован в текущей версии
протектора и служит фундаментом. Известное слабое место — статический вывод ключей
шифрования строк из имени класса — закрывается в Рубеже B (§6.4).

---

## 6. Рубеж B — поток управления и строки

Это апгрейд текущего протектора и **самый высокий ROI** на первой фазе.

### 6.1. Chunk: decrypt → execute → wipe

**Принцип.** Метод разбивается на этапе сборки на N логических блоков (basic blocks по
границам CFG). Каждый блок:

1. Хранится в class-файле в **зашифрованном** виде как байтовый массив в constant pool.
2. Расшифровывается непосредственно перед входом в блок — через сгенерированный bootstrap-вызов.
3. Исполняется.
4. Сразу после выхода **затирается**. Простой `Arrays.fill(buf, 0)` JIT может выкинуть как
   dead store, поэтому применяем `Reference.reachabilityFence` + volatile-запись **или**
   вызов native zero-wipe через JNI, который JIT не имеет права элиминировать.

Схема трансформации одного метода:

```
исходник:                 защищённый вид:
  block_A                   key_A = deriveKey(state)
  block_B          →        buf_A = decrypt(enc[0], key_A); exec(buf_A); wipe(buf_A)
  block_C                   key_B = deriveKey(state')        // state' зависит от block_A
                            buf_B = decrypt(enc[1], key_B); exec(buf_B); wipe(buf_B)
                            ...
```

**Ключевой инвариант (scope-binding).** `state` для деривации ключа следующего блока обязан
зависеть от **результата исполнения предыдущего** блока — например, хэш от значений
нескольких локальных переменных в момент выхода. Тогда дамп блока B в изоляции от реального
прохода через блок A не позволяет его расшифровать: ключ исторически зависим от пути исполнения.

### 6.2. Деривация ключей — HKDF от составного контекста

Источники энтропии для `state` (комбинируются через HKDF-Extract):

1. Время с момента старта JVM (снимок `System.nanoTime()` на старте, не абсолютное время).
2. Хэш набора загруженных classloader'ов на момент вызова (меняется при подмене classloader под дамп).
3. Значение из нативного слоя (Рубеж D), полученное через JNI — связывает Java- и native-слои
   так, что дамп одного бесполезен без другого.
4. Опционально: хэш нескольких «контрольных» полей объекта-владельца метода (выбираются
   ASM-пассом случайно на этапе защиты).

### 6.3. Control-flow flattening + opaque predicates

- CFG метода конвертируется в dispatch-loop: `while (true) { switch (state) { ... } }`.
- Переходы состояний кодируются **не литералами**, а результатом opaque predicate:
  `state = ((x*x - x) % 2 == 0) ? NEXT_A : NEXT_B` — математически всегда `NEXT_A`, но
  статический анализатор должен доказывать это через нетривиальный constraint solving.
- Flattening применяется **выборочно** — только к методам, помеченным аннотацией `@Guarded`.
  Тотальный flattening убивает производительность real-time кода (детект-цикл с жёсткими
  временными ограничениями).

### 6.4. Шифрование строк и констант — апгрейд

- **Проблема текущей версии:** ключ выводится статически из имени класса.
- **Решение:** ключ строки = `HKDF(per-build master secret, class-hash, string-index)`.
  `per-build master secret` генерируется на CI заново на каждый билд и инжектится через
  build-time патчинг байткода в нативный слой (Рубеж D). В Java-classfile его нет вообще.

## 7. Рубеж C — полиморфная виртуальная машина

### 7.1. Что виртуализировать (и что нет)

Полная виртуализация всего кода избыточна и убьёт tick-performance real-time продукта.
Виртуализируем только самое ценное IP:

- алгоритмы детекта / ядро продукта;
- логику license/integrity check;
- ключевые математические преобразования (feature-extraction формулы и т.п.).

### 7.2. Архитектура интерпретатора

- **Stack-based VM** — проще генерировать код, проще JIT-компилировать сам интерпретатор.
- **40–60 базовых опкодов** (ARITH, LOAD, STORE, CALL_NATIVE, BRANCH, …), намеренно
  избыточный набор: одна семантика достижима через 3–4 разных опкода, выбор случаен на
  этапе генерации байткода под конкретный билд.
- **Полиморфизм** (P5): таблица `opcode → handler` перемешивается перестановкой на каждую
  сборку из seed'а CI build number. Диспетчеризация — **не** `switch/case` (легко находится
  по сигнатуре jump table), а computed indirect call по таблице указателей, которая сама
  зашифрована в стиле Рубежа B (chunk decrypt-execute-wipe применяется и к телу интерпретатора).

### 7.3. Где живёт интерпретатор — два варианта

Поддерживаем оба, выбираем по ценности защищаемого алгоритма:

| Вариант | Плюс | Минус | Когда |
|---------|------|-------|-------|
| **Java-интерпретатор** | быстрая разработка | компрометация даёт универсальный девиртуализатор для всех Java-методов билда (митигируется полиморфизмом ISA per-build) | ранняя фаза, 3–5 ценных алгоритмов |
| **Native-интерпретатор (Rust, через JNI)** | на порядок дороже для реверса — нужен IDA/Ghidra + понимание кастомного ISA одновременно | дорогая разработка | самые ценные алгоритмы, поздняя фаза |

## 8. Рубеж D — нативный самозащитный барьер (Rust)

### 8.1. Назначение

- проверка лицензии / HWID;
- integrity-check Java-слоя (хэши class-файлов в рантайме против подписанного манифеста);
- anti-debug на OS-уровне;
- источник энтропии для HKDF-деривации ключей Рубежей B/C через JNI.

### 8.2. Anti-debug — минимум четыре независимых механизма (P3)

Каждый деградирует состояние **по-своему** и **без явного abort** (P4):

1. **JVMTI/агент-детект.** Анализ `ManagementFactory.getRuntimeMXBean().getInputArguments()`
   на `-agentlib` / `-javaagent` / `-Xdebug` / `jdwp`. При срабатывании — не бросать
   исключение, а подменить один байт в derived key Рубежа B так, чтобы расшифровка следующего
   chunk дала **валидный, но слегка изменённый** байткод (например, off-by-one в пороге
   алгоритма). Это выглядит как баг, а не как защита, и резко удлиняет диагностику для атакующего.
2. **Timing-checks.** Измерение длительности известного по времени участка через `rdtsc` в
   Rust-слое. Аномальное замедление = debugger/single-step → та же тихая деградация.
3. **Hardware breakpoint detection.** Проверка debug-регистров: DR0–DR7 на Windows через
   `GetThreadContext`, на Linux — `ptrace(PTRACE_PEEKUSER, …)` на собственный поток.
4. **Self-attach test.** Периодическая попытка self-attach через Dynamic Attach API. Не
   удаётся (JVM занята легитимным дебаггером) → сигнал тревоги.

### 8.3. Integrity-check — распределённый, не единая функция

Не `boolean checkIntegrity()`, а **50–100 мелких проверок**, инжектируемых ASM-пассом в
случайные точки прогона (не только в очевидные места вроде старта). Каждая проверяет хэш
одного case-блока/метода, и результат используется **не** в `if/throw`, а как часть
арифметики следующего вычисления — например, входит множителем в деривацию ключа следующего
chunk. Не совпал хэш → ключ неверный → расшифровка даёт мусор без явного failure.

### 8.4. Самозащита нативного слоя

- **Собственный минимальный packer** для `.dll`/`.so` — **не** готовый VMProtect/Themida:
  они сигнатурятся AV/EDR, и для них есть публичные unpacker'ы (хуже, чем отсутствие паковки).
- Простая своя схема: ChaCha20/XOR поверх `.text`-секции; unpack-stub в начале расшифровывает
  остальное в exec-memory на старте и затем **затирает сам stub** из памяти.
- **Обфускация экспортов:** никаких говорящих `Java_com_..._` имён. Ручная регистрация через
  `JNI_OnLoad` вместо стандартного naming convention — прячет факт JNI-привязки от поверхностного анализа.

## 9. Рубеж E — сборка и дистрибуция

### 9.1. Полиморфизм на уровне сборки

- Каждый релизный билд — уникальная перестановка: опкоды ISA, порядок integrity-проверок,
  набор opaque predicates, границы chunk'ов — всё выводится из CI build-seed.
- **Никогда** не переиспользовать одну protected-сборку для нескольких клиентов. Если
  экономика позволяет — каждому покупателю отдельный полиморфный билд. Это резко повышает
  стоимость сценария «взломать один раз и раздать крак всем».

### 9.2. Кастомный JRE — применимость

- Для **standalone-клиента с собственным лаунчером** оправдан: разработчик контролирует, какой
  JRE запускает пользователь.
- Для **серверного плагина** — нет: владелец сервера сам выбирает JVM, навязать образ нельзя без
  большого трения для покупателей. В этом случае Рубеж F не делаем, бюджет вкладываем глубже в
  Рубежи C–D.

## 10. Рубеж F (опциональный) — кастомный JRE через JVMTI-хуки

Реалистичный потолок без патчинга исходников HotSpot. Даёт большую часть эффекта custom JRE
при кратно меньших трудозатратах, чем правка `bytecodeInterpreter.cpp`. Подходит под кейс
«платный визуальный мод, распространяется игрокам, защищаем от крака/дампа/слива сурсов».

**Принцип.** Не патчим интерпретатор байткода, а перехватываем точки входа, которыми
пользуются публичные dump-инструменты (Recaf attach-mode, JVMTI retransform-дамперы,
async-profiler), и либо блокируем их, либо отдаём заведомо нерабочие данные.

**Компоненты:**

1. **Свой JVMTI-агент**, зашитый прямо в `lib/modules` jlink-образа на этапе сборки
   дистрибутива (не подключаемый снаружи через `-agentlib`). Стартует раньше, чем что-либо
   стороннее успевает подключиться.
2. **Перехват Instrumentation-pipeline.** Агент регистрирует `ClassFileLoadHook` с максимальным
   приоритетом раньше любого стороннего. Появление второго Instrumentation-агента (детект через
   мониторинг создания Dynamic Attach socket/named-pipe) → тихая деградация: следующие
   chunk-расшифровки получают на один байт другой derived key.
3. **Защита Dynamic Attach целиком.** Загрузчик выставляет `jdk.attach.allowAttachSelf=false`
   и фильтрует attach по allow-list PID (только процесс лаунчера). Блокирует целый класс
   инструментов поверх Dynamic Attach API.
4. **Memory-dump детект общего вида.** Периодическая (jittered random interval, не фиксированный
   таймер) проверка артефактов suspend-resume всего процесса — типичный побочный эффект момента,
   когда внешний инструмент приостанавливает JVM для консистентного снимка памяти.

**Трудозатраты.** Совместимо с Rust-барьером (Рубеж D): JVMTI-агент пишется через `jvmti.h`
FFI-биндинги. Реалистично ~6–10 недель соло, без правки исходников HotSpot.

---

## 11. Контур самопроверки (redteam)

Обязательный модуль `:ruguard-redteam` превращает «мы думаем, что защита хорошая» в измеримый,
регрессионно тестируемый инвариант.

- На каждый CI-билд автоматически прогоняются стандартные dump-инструменты: Recaf attach-mode,
  JVMTI class-retransform дамперы, async-profiler memory dump.
- Если редтим-тест **проходит** (дамп дал валидный исполняемый classfile) — билд **не публикуется**.
  Это баг защиты, а не фича.
- Редтим — это твой собственный «реверсер»; задача — чтобы он ломался как можно дольше.

## 12. Дорожная карта

Строго в этом порядке. **Каждая фаза обязана пройти redteam-gate перед следующей.**
Каждая фаза — отдельный PR с прогоном редтима, не «большой бэнг» мердж.

| Фаза | Содержание | Зависит от |

## 13. Границы и ограничения

- **Не** реализовывать обход конкретных коммерческих EDR/AV-продуктов.
- **Не** копировать байты/структуры сторонних протекторов — только независимая реализация по
  принципам из этого документа, не reverse-engineered клон.
- Каждая фаза — отдельный PR с прогоном редтима, не один большой мердж.

## 14. Итоговая оценка

Полный путь (Фазы 1–6, включая вариант Рубежа F через JVMTI-хуки, без полного HotSpot-патчинга)
— ориентировочно **9–14 месяцев соло** без спешки, параллельно с основной загрузкой. Это не
«идеально и навсегда» — это уровень, при котором крак требует от атакующего недель
целенаправленной работы профильного реверс-инженера, что для большинства крякеров
экономически нерентабельно относительно цены подписки.

Полный HotSpot-патчинг (отказ от JVMTI-хуков в пользу прямой правки интерпретатора) — отдельный
проект сопоставимой с самим продуктом сложности. Начинать его только если после полного цикла
Фаз 1–6 редтим реально найдёт рабочий обход именно на уровне JVMTI-барьера.

## Приложение. Инструкция агенту (project-инструкция)

> Отдаётся агенту как system/project-контекст. Агент работает по фазам §12, не пропуская
> redteam-gate между ними.

Ты разрабатываешь protector-тулчейн **RuGuard** для коммерческого JVM-мода (визуальный, без
читерских модулей, продаётся по подписке). Цель — защита от кракинга подписки, дампа
байткода, декомпиляции и слива исходников. Источник истины — `RuGuard-spec.md`.

**Незыблемые правила (§2), не нарушать:**
1. Никогда весь защищённый артефакт не расшифрован в памяти целиком одновременно.
2. Ни один ключ не статическая константа — всегда производная от runtime-состояния.
3. Каждый защитный инвариант проверяется минимум тремя независимыми механизмами.
4. Провал проверки — тихая деградация, не explicit throw/exit.
5. ISA виртуальной машины полиморфен между сборками (build-seed из CI).
6. Native-слой самозащищён отдельно от Java-слоя.

**Структура репозитория** (Gradle multi-module + Cargo workspace):
```
:ruguard-cli       — Kotlin, ASM-трансформер этапа сборки
:ruguard-runtime   — Java-рантайм (VM-интерпретатор, до Фазы 5)
:ruguard-native    — Rust: JNI-барьер, JVMTI-агент, native VM-интерпретатор
:ruguard-redteam   — самотестирование: dump/attach-атаки на каждый CI-билд
```

**Порядок работы — строго по фазам §12.** После каждой фазы:
- прогнать `:ruguard-redteam` против собранного билда;
- билд не завершён, пока редтим-тест не показывает провал атаки;
- только после этого — следующая фаза.

**Scope (§13):**
- не реализовывать обход конкретных коммерческих EDR/AV-продуктов;
- не копировать байты/структуры сторонних протекторов — только независимая реализация;
- каждая фаза — отдельный PR с прогоном редтима.

При любой неоднозначности сверяться с инвариантами §2, не с «что нагляднее/быстрее закодить».
